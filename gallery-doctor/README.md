# רופא הגלריה (Gallery Doctor)

אפליקציית אבחון לאנדרואיד שמסבירה, בעברית פשוטה, **למה אפליקציית הגלריה בטלפון קורסת או נטענת מחדש**.
היא לא סתם מציגה רשימת קבצים: היא בודקת קבצים, אינדקס מדיה ואחסון, ומדרגת את הסיבות האפשריות לפי הראיות שנמצאו.

* **קריאה בלבד.** האפליקציה לא מוחקת, לא מזיזה ולא משנה אף קובץ. כל פעולה בדוח היא המלצה שמבצעים ידנית.
* **אופליין לגמרי.** אין הרשאת `INTERNET`, אין אנליטיקס ואין העלאה לענן.
* **שלושה מסכים בלבד:** התחלה, התקדמות, דוח. עברית מלאה, כיווניות RTL, גופן גדול, ערכת נושא בהירה וכהה.

## מה היא בודקת

| תחום | מה נבדק |
|---|---|
| **שלמות קבצים** (3 שלבים, מהזול ליקר) | **L1** גודל 0, חתימת קובץ (magic) מול סיומת, מידות התמונה. **L2** מבנה פנימי: JPEG (SOI/EOI, שרשרת סמנים, חיתוך), PNG (IEND ו-CRC של כל חלק), WebP (גודל RIFF), HEIC (ftyp ומבנה), MP4/MOV/3GP (ftyp, **moov חסר = הקלטה שנקטעה**, גודל mdat מול גודל הקובץ, ערוץ אחד לפחות), שגיאות EXIF. **L3** פענוח אמיתי בגודל מוקטן, ובסרטונים חילוץ פריים מהאמצע ומהסוף. |
| **בידוד קריסות** | כל פענוח מסוכן רץ בתהליך נפרד (`:scanner`). קריסה של מפענח מערכת הפעלה הורגת את תהליך הבדיקה ולא את האפליקציה. קובץ שקורס או נתקע (מעל 5 שניות) מסומן **CRASHER** והסריקה ממשיכה. |
| **אינדקס המדיה** | רשומות רפאים (באינדקס אבל לא קיימות), קבצים שחסרים באינדקס, `IS_PENDING` תקוע מעל 24 שעות, קבצי `.pending-*`/`.trashed-*` ישנים, תיקיות עם יותר מ-5,000 קבצים, ויציבות האינדקס: כמה רשומות השתנו או נעלמו בין שתי קריאות במרווח 60 שניות. |
| **אחסון** | מקום פנוי בכל כרך (קריטי מתחת ל-10% או 2GB), פילוח תמונות/סרטונים/תיקיות גדולות, שגיאות קריאה, מהירות קריאה, קבצים שנקראים אחרת בקריאה חוזרת (סימן לכרטיס SD או אחסון תקול), ואילו אפליקציות גלריה מותקנות ובאילו גרסאות. |
| **חריגות** | תמונות מעל 50 מגה-פיקסל, צלע מעל 16,384, קובץ מעל 30MB, פנורמות קיצוניות, סרטונים מעל 2GB, 8K, 4K בקצב נתונים גבוה, מעל 60fps, אורך 0 או חריג. |
| **כפילויות** | קיבוץ לפי גודל, אחר כך hash חלקי (64KB ראשונים + 64KB אחרונים), ורק על המועמדים הנותרים SHA-256 מלא. הדוח מציג כמה מקום אפשר לפנות. |

## הדוח

1. **אור רמזור ומשפט אחד** שמסכם את המצב.
2. **הסיבות הסבירות ביותר**, מדורגות, עם רמת ביטחון (גבוהה/בינונית/נמוכה) וראיות. למשל "קובץ X קרס את המפענח" או "42 רשומות רפאים באינדקס".
3. **צעדים מעשיים** בעברית, ולכל צעד הסבר *למה הוא רלוונטי לראיות שנמצאו*.
4. **טבלאות**: קבצים שקרסו, פגומים, חשודים, חריגים, כפילויות, תיקיות כבדות. בכל שורה כפתור **פתח** שפותח את הקובץ באפליקציית המערכת, כדי לבדוק אותו ידנית.
5. **שיתוף**: טקסט, PDF, ו-CSV של כל הקבצים הבעייתיים (UTF-8 עם BOM, נפתח נכון באקסל).
6. **מגבלות, בכנות.** האפליקציה לא יכולה לקרוא יומני קריסה של אפליקציות אחרות. הדירוג מבוסס על ראיות, לא על מה שהגלריה עצמה דיווחה.

### איך לקרוא את רמת הביטחון

| רמה | משמעות |
|---|---|
| **גבוהה** | ראיה חזקה ישירה, למשל קובץ שקרס את המפענח בבדיקה, או אינדקס שמשתנה בלי הפסקה. |
| **בינונית** | ראיה חזקה שעשויה לתרום לבעיה אבל אינה מוכיחה אותה, למשל אחסון כמעט מלא. |
| **נמוכה** | ניחוש סביר בלי ראיה ישירה, למשל "מטמון פגום". זה מופיע גם כשלא נמצא דבר אחר, כי התיקון זול ובטוח. |

### הדרך הכי טובה לדעת בוודאות מה קורס

האפליקציה לא יכולה לראות את יומן הקריסה של הגלריה, אבל מחשב יכול. מחברים את הטלפון במצב ניפוי USB ומריצים:

```
adb logcat -b crash
```

פותחים את הגלריה עד שהיא קורסת, והשורות `FATAL EXCEPTION` או `signal 11` בפלט מראות מה בדיוק נפל ובאיזה קובץ.

## בנייה

דרישות: **JDK 17**, **Android SDK** עם פלטפורמה 36 (Android Studio מתקין אותה אוטומטית), וחיבור לאינטרנט בפעם הראשונה כדי להוריד תלויות.

```bash
cd gallery-doctor
./gradlew assembleDebug          # בונה APK לניפוי
./gradlew testDebugUnitTest      # מריץ את בדיקות היחידה
```

ה-APK נוצר בנתיב `app/build/outputs/apk/debug/app-debug.apk`.
ב-Android Studio: File ← Open ← התיקייה `gallery-doctor`, ואז Run.

> גרסאות Gradle, AGP, Kotlin ו-Compose מוגדרות ב-`build.gradle.kts` וב-`app/build.gradle.kts`.
> אם גרסה לא נמצאה אצלכם ב-Maven, מעדכנים אותה לגרסה העדכנית היציבה.

### גרסת release חתומה

1. יוצרים מפתח חתימה (פעם אחת, ושומרים אותו במקום בטוח, גם גיבוי שלו):

   ```bash
   keytool -genkeypair -v -keystore gallery-doctor.jks -alias gallerydoctor \
     -keyalg RSA -keysize 4096 -validity 10000
   ```

2. מעתיקים את `keystore.properties.example` ל-`keystore.properties` (הקובץ מוחרג מ-git) ומעדכנים בו את הנתיב והסיסמאות.
3. בונים:

   ```bash
   ./gradlew assembleRelease
   ```

   התוצאה: `app/build/outputs/apk/release/app-release.apk`. ללא `keystore.properties` ייווצר APK לא חתום, שאנדרואיד לא יתקין.
4. בדיקת החתימה (כלי `apksigner` נמצא ב-`build-tools` של ה-SDK):

   ```bash
   apksigner verify --verbose app/build/outputs/apk/release/app-release.apk
   ```

אפשר גם לבנות בלי להתקין שום דבר: ב-GitHub, ה-workflow `.github/workflows/gallery-doctor.yml` בונה APK ומריץ את הבדיקות בכל push. את ה-APK מורידים מלשונית Actions ← הריצה ← Artifacts.

## התקנה בטלפון (sideload)

1. מעבירים את `app-debug.apk` (או `app-release.apk`) לטלפון: כבל USB, WhatsApp לעצמכם, Google Drive או מייל.
2. פותחים את הקובץ בטלפון. אנדרואיד ישאל אם לאפשר התקנה ממקור לא ידוע: מאשרים לאפליקציה שממנה פתחתם (הדפדפן, Files או WhatsApp), בהגדרות ← "התקנת אפליקציות לא מוכרות".
3. ייתכן ש-Google Play Protect יציג אזהרה על אפליקציה לא מוכרת. בוחרים "התקן בכל זאת". האפליקציה לא נשלחת לשום מקום, והקוד פתוח לבדיקה.
4. או דרך מחשב: מפעילים ניפוי USB בטלפון ומריצים `adb install -r app-debug.apk`.
5. פותחים את "רופא הגלריה", לוחצים **התחל סריקה**, ומאשרים גישה ל**כל** התמונות והסרטונים. גישה חלקית ("רק תמונות שנבחרו") לא מספיקה לאבחון.

## שימוש

* **התחל סריקה**: סריקה מלאה. מומלץ להשאיר את הטלפון מחובר לחשמל. עשרת אלפים קבצים לוקחים בדרך כלל כמה דקות, וחמישים אלף כמה עשרות דקות.
* **סריקה מהירה** (מתג): בלי בדיקת פענוח. מהירה בהרבה, אבל לא מזהה קבצים שמקריסים את הגלריה, ולכן פחות מדויקת.
* **בחירת תיקייה**: סריקה של תיקייה מסוימת, כולל כרטיס SD. נמצאים קבצים שהגלריה לא רואה.
* אפשר **לעצור** ולהמשיך אחר כך. המצב נשמר במסד נתונים מקומי קטן.
* אם הטלפון מתחמם מאוד, הסריקה מושהית אוטומטית לכמה שניות.

## ארכיטקטורה בקצרה

```
UI (Compose, 3 מסכים)
  └─ ScanController + ScanService (foreground)     ← תהליך ראשי: אורקסטרציה, מסד נתונים, ניתוח
        ├─ MediaEnumerator / SafEnumerator          ← MediaStore ותיקייה שנבחרה, בקבוצות של 1,000
        ├─ FsWalker                                 ← יתומים וקבצים זמניים בתיקיות המדיה
        ├─ ScanCoordinator  ──(Messenger)──►  :scanner, :scanner2, :scanner3   ← תהליכי מפענחים מבודדים
        │      watchdog, ניסיון חוזר, סימון CRASHER        FileTester: L1 + L2 + L3, קריאה בלבד
        ├─ DuplicateFinder, IndexStability
        └─ Analyzer → ReportDocument → טקסט / PDF / CSV
```

* `core/` – קוד Kotlin נקי בלי תלות באנדרואיד (פרסרים, מתאם הסריקה, מנתח הסיבות, בניית הדוח). זה מה שנבדק ב-JVM.
* `worker/` – מה שרץ בתהליכים המבודדים והלקוח שמפקח עליהם.
* כל קובץ נבדק על ידי **תהליך אחד בכל פעם**, ולכן קריסה תמיד משויכת לקובץ אחד בדיוק.
* לפני כל קובץ נרשם במסד "בודקים עכשיו: X". אם התהליך או האפליקציה מתים, בהפעלה הבאה הקובץ נבדק שוב (ניסיון נוסף), ואחרי כישלון שני הוא מסומן CRASHER.

* **תוכנית בדיקה ידנית** על מכשיר אמיתי: [`docs/TEST_PLAN.md`](docs/TEST_PLAN.md).
* **תכנון וסיכונים:** [`docs/PLAN_AND_RISKS.md`](docs/PLAN_AND_RISKS.md).

### בדיקת בידוד הקריסות

בגרסת **debug** בלבד, קובץ מדיה ששמו מתחיל ב-`GD_TEST_CRASH_` מקריס בכוונה את תהליך הבדיקה, וקובץ ששמו מתחיל ב-`GD_TEST_HANG_` נתקע בכוונה. בגרסת release הקוד הזה לא פעיל. ראו את התוכנית הידנית.

## אימות הקוד מול דרישות הפרטיות

```bash
# אין INTERNET ואין MANAGE_EXTERNAL_STORAGE
grep -n "INTERNET\|MANAGE_EXTERNAL_STORAGE" app/src/main/AndroidManifest.xml     # אמור להחזיר רק שורת הערה
# אין כתיבה או מחיקה של מדיה: הקבצים נפתחים רק במצב "r"
grep -rn "openOutputStream\|\.delete(\|MediaStore.*delete\|contentResolver.*delete\|\"rw\"\|\"w\"" app/src/main/java
```

הפקודה השנייה לא אמורה להחזיר דבר. אפשר גם לוודא את ההרשאות ב-APK שנבנה: `apkanalyzer manifest permissions app-debug.apk`.
כתיבה מתבצעת רק למסד הנתונים של האפליקציה ולתיקיית המטמון שלה (קבצי PDF ו-CSV לשיתוף).

## מגבלות ידועות

* אי אפשר לקרוא יומני קריסה של אפליקציות אחרות. הדירוג מבוסס על ראיות.
* בדיקת המבנה (L2) מכסה JPEG, PNG, WebP, HEIC ו-MP4/MOV/3GP. פורמטים אחרים (GIF, BMP, MKV, AVI) נבדקים רק בכותרת ובפענוח (L1 ו-L3), ולכן חיתוך בהם מזוהה רק אם הפענוח נכשל.
* קובץ MP4 מקוטע (fragmented) שנחתך בדיוק בגבול בין שני קטעים נראה תקין מבנית, כי אין בו סימן שמשהו חסר.
* חיפוש קבצים שחסרים באינדקס מתבצע רק בתיקיות המדיה הרגילות ובתיקייה שנבחרה, כי אנדרואיד 11 ומעלה לא מאפשר לסרוק את כל האחסון.
* רשומות `IS_PENDING` של אפליקציות אחרות לא תמיד נראות לאפליקציה שלנו.
* באנדרואיד 8 (API 26) חילוץ פריים מסרטון לא מוקטן על ידי המערכת, וסרטוני 8K עלולים להיכשל שם מחוסר זיכרון, ויסומנו ככאלה.
* תקיעה של יותר מ-5 שניות מסומנת כחשד לקריסה רק אחרי ניסיון שני עם 20 שניות, כדי לא להאשים קובץ בגלל אחסון איטי.
