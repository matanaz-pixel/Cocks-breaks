# Site audit

The project is a Hebrew RTL static site (`site/`) plus a one-file offline editor (`editor/site-editor.html`) that a non-technical owner uses to change texts, photos and testimonials. This skill checks it from four angles and returns one prioritised report in Hebrew.

## Procedure

1. **Build and run the automated tests first.**
   ```
   cd site && npm run build && npm test
   ```
   Playwright must be installed. If it lives elsewhere, set `PLAYWRIGHT_PATH` (in this cloud environment: `/opt/node22/lib/node_modules/playwright`). Test photos are generated by `tests/make-fixtures.py` (needs Pillow). Record the pass/fail counts. A failing test is a finding by itself.
2. **Launch four independent agents in parallel** (Agent tool, `general-purpose`, background). Each agent reads its own brief and returns a report in Hebrew:
   - `briefs/mechanical.md`: bugs, robustness, data loss, security, cross-browser gaps.
   - `briefs/design.md`: visual design, UX, copy, accessibility, the editor's usability for a non-technical user.
   - `briefs/legal.md`: Israeli legal and regulatory risks in what the site says and collects.
   - `briefs/admin.md`: ownership, accounts, domain, hosting, email, backups, maintenance and launch readiness.

   Prompt template for each agent: *"Read `/home/user/Cocks-breaks/.claude/skills/site-audit/briefs/<name>.md` and follow it exactly. Repo: `/home/user/Cocks-breaks`. Do not modify any file inside the repo. Put scripts and screenshots in your scratchpad directory only. Final report in Hebrew, at most 700 words."*
3. **Do not fix anything while the agents run.** They read the same files.
4. **Merge the four reports** into one Hebrew answer:
   - one-line verdict: ready to publish, ready after fixes, or not ready;
   - a table of confirmed findings sorted by severity (critical, high, medium, low), with who acts: *Claude can fix*, *the owner must decide or supply*, *needs a professional* (lawyer, accountant, accessibility consultant);
   - separately: suspected but unverified items, and what could not be tested and why;
   - de-duplicate findings that several agents reported.
5. **Fixing.** Fix mechanical and design findings only after the user agrees on scope. Add a regression test in `site/tests/` for every bug that gets fixed. Never decide a legal or administrative question on the owner's behalf: present the options and say a professional should confirm.

## Rules for every agent

- Reproduce a suspected bug twice and show evidence (viewport, steps, measured numbers). Separate "confirmed", "cosmetic" and "could not reproduce".
- Known placeholders are not bugs: the name "שם היועצת", phone 050-000-0000, `example.com` email, generic social links, testimonials tagged "דוגמה", icon tiles standing in for photos. They are launch-blockers, though, and the audit must list them once under administrative readiness.
- Findings must name the exact file, selector, field or sentence. No generic advice.
- Legal findings are not legal advice. Say what the risk is, why, how confident you are, and what a professional should confirm. Verify current law with web search when a search tool is available, and cite the source.
